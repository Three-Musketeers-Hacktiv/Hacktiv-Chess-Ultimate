# AGENTS.md

## Backend scope

Build the Hacktiv Chess MVP in this `server` directory.

## Current milestone

- Authentication and the PvP playable flow are implemented: random matchmaking by selected time control, queue cancellation, legal moves, persisted history, game clocks, core game endings, read-only watching, and Socket.IO updates. Keep these working while adding future features.
- Bot games are available only when the executable configured by `STOCKFISH_PATH` can be accessed; home must report that runtime capability accurately. A full UCI move test is required before reporting the engine integration verified.
- Authenticated `GET /api/games` provides a user's PvP and bot game summaries using cursor pagination; keep ownership checks and stable ordering when changing this endpoint.
- The `README.md` and `API.md` must distinguish implemented behavior from planned behavior whenever code changes.

## Stack and architecture

- Use Node.js with Express for the REST API.
- Use PostgreSQL with Sequelize for persistent users, games, and ordered move history. Follow `DATABASE_SCHEMA.md` for the reviewed database design.
- Treat FEN as a snapshot of one board position and PGN as an ordered game record. Persist structured moves as the source for history; derive PGN when needed and keep the current FEN on the game.
- Keep database models and migrations aligned with this schema:
  - `users`: `id UUID` primary key; `username VARCHAR(24)` and `email VARCHAR(254)` required and unique; `password_hash VARCHAR(255)` required; `created_at` and `updated_at TIMESTAMPTZ` required. Normalize username and email to lowercase before storage and login.
  - `games`: `id UUID` primary key; required `mode VARCHAR(8)` (`pvp`/`bot`) and `status VARCHAR(16)` (`waiting`/`in_progress`/`completed`); `time_control_minutes SMALLINT` and `increment_seconds SMALLINT` must be one of `(1,0)`, `(3,2)`, `(15,10)`, `(60,30)`; nullable `bot_difficulty VARCHAR(8)` (`easy`/`medium`/`hard`, required only for bot); required `white_player_id UUID` FK to users; nullable `black_player_id UUID` FK to users; required `current_fen TEXT`; required `white_time_remaining_ms`/`black_time_remaining_ms BIGINT`; nullable `turn_started_at TIMESTAMPTZ`; nullable `draw_offer_by_player_id UUID` FK to users; nullable `result VARCHAR(7)` (`1-0`/`0-1`/`1/2-1/2`) and `termination_reason VARCHAR(32)`; `created_at`, nullable `started_at`/`ended_at`, and required `updated_at` as `TIMESTAMPTZ`.
  - `game_moves`: `id UUID` primary key; required `game_id UUID` FK; positive `ply INTEGER`; required `actor_type VARCHAR(8)` (`player`/`bot`); nullable `player_id UUID` FK (null for bot); `color CHAR(1)` (`w`/`b`); `from_square` and `to_square CHAR(2)`; nullable `promotion CHAR(1)` (`q`/`r`/`b`/`n`); required `san VARCHAR(32)`, `fen_after TEXT`, and `created_at TIMESTAMPTZ`.
  - Enforce unique `username`, `email`, and (`game_id`, `ply`); a partial unique index for one waiting PvP queue per `white_player_id`; foreign keys; allowed-value and lifecycle checks; player/color/mode consistency; and indexes on (`white_player_id`, `created_at`), (`black_player_id`, `created_at`), and (`mode`, `status`, `created_at`). A game has many moves; users may be white or black. Keep `game_moves` as the history/PGN source and `games.current_fen` as the current position.
  - `draw_offer_by_player_id` is allowed only for PvP and must reference a game player; it must be null for bot games. Allow `termination_reason` values `checkmate`, `stalemate`, `dead_position`, `resignation`, `timeout`, `draw_agreement`, `threefold_repetition`, `fivefold_repetition`, `fifty_move_rule`, `seventy_five_move_rule`, and `engine_failure`.
  - Follow `DATABASE_SCHEMA.md` for the ER diagram and transaction behavior. Create constraints and indexes in migrations, not only model validations.
- Use Socket.IO for real-time PvP move notifications and game events. The server owns and validates canonical game state.
- Pin `chess.js` v1.4.0 in the lockfile. Use it on the server to validate legal moves from both players and Stockfish, maintain canonical positions, and generate FEN/PGN. Use Stockfish only to choose bot moves and analyze PGN. Implement fivefold repetition and the automatic 75-move rule in the game service: replay the complete move history from the initial position and count a canonical position key that includes piece placement, side to move, castling rights, and legal en-passant availability. Do not rely on unreleased `chess.js` draw-rule APIs. Read the engine path from `STOCKFISH_PATH`; do not hard-code machine-specific paths.
- Organize code by responsibility under `src/config`, `src/models`, `src/middleware`, `src/routes`, `src/services`, and `src/socket`.

## MVP boundaries

- Prioritize authentication, PvP and bot games, server-side legal move validation, saved PGN/game history, basic win-draw-loss statistics, and Stockfish analysis.
- Implement the selected time controls for both modes: Bullet 1+0, Blitz 3+2, Rapid 15+10, and Professional 60+30 (minutes + seconds increment). Store remaining clocks and the active turn start in PostgreSQL; the server clock is authoritative.
- API preset IDs and labels: `bullet` (Sangat Cepat), `blitz` (Cepat), `rapid` (Reguler), and `professional` (Professional). Players are matched only with another queued player using the same preset; clocks start when the match is made.
- End games on checkmate, stalemate, positions recognized by `chess.js` `isInsufficientMaterial()`, fivefold repetition, the 75-move rule, timeout, resignation, or an agreed draw. Keep MVP draw handling practical rather than implementing exhaustive FIDE dead-position analysis or promising exact Chess.com parity. On timeout, award a draw only when `isInsufficientMaterial()` returns `true` for the whole position; otherwise the player who flagged loses. Resignation is a loss for the resigning player while the game is active. Support player claims for threefold repetition and the 50-move rule only for the current position; do not support claims based on an intended move in the MVP. Validate claims against move history. A failed claim adds two minutes to the opponent clock.
- Support one pending draw offer at a time. A player may offer after both players have made a move; the opponent can accept or decline, and making a move rejects the offer. Persist its offering player ID and clear it when answered or when the game ends.
- Keep clocks correct after reconnects and server restarts: derive elapsed time from persisted `turn_started_at`, restore active games, and detect expired clocks before accepting moves or resuming a game.
- Capture each state-changing game request's server `receivedAt` at handler entry, before validation or database work. For a move, treat it as on time only when `receivedAt` is strictly earlier than the active clock deadline; an equal or later timestamp is a timeout. Apply the same deadline-first rule to resignations, draw offers, and draw claims so a late action cannot bypass or reverse a flag fall. Illegal moves do not stop or reset the clock. Use UTC server time and keep the app/database host clocks synchronized.
- Serialize state-changing requests and timeout handling through a per-game queue for the single MVP server instance. Calculate the mover's elapsed time from move `receivedAt`, apply increment only after a legal move, and start the opponent clock after the move is committed. Do not let a timeout job overtake an earlier-received request.
- Run a server-side timeout scheduler for in-progress games so a flag fall ends the game even if no client sends another request; reconcile timers from PostgreSQL at startup. Multi-instance deployment requires a shared ordering mechanism; an in-memory queue is only valid for one server instance.
- Bot games require `easy`, `medium`, or `hard`, mapped to Stockfish `Skill Level` 0, 5, or 10 respectively. Treat these as relative levels, not Elo promises; never set `Skill Level` and `UCI_Elo` together or accept raw UCI options from clients. Read the executable from `STOCKFISH_PATH`; do not commit a local binary or machine-specific path. Run at most two Stockfish processes concurrently, each with `Threads = 1`, plus at most five waiting jobs; cap bot search at 1000 ms per move. Reserve a bot queue slot before committing a human move in a bot game; if capacity is unavailable, return `503 ENGINE_BUSY` without saving that move. Release the reservation if validation or the transaction fails. Return the accepted human move immediately with `bot_move_pending: true`; after the engine move is validated and committed, broadcast it through Socket.IO. Before saving an engine result, recheck under a transaction that the game is active, it is still the bot's turn, the FEN is unchanged, and the bot clock has not expired. If Stockfish fails, end the game as a draw with `engine_failure` so neither side loses because of a server error. On startup, resume active bot games whose persisted position shows it is the bot's turn. A full engine queue must keep a recovered game active and retry it later; only an unavailable engine finalizes it as `engine_failure`. Database or other transient recovery errors are logged and retried, not converted to engine failures.
- Require registration and login before a player can enter or cancel PvP matchmaking. Use the authenticated user ID as the owner of games, history, and statistics.
- After successful login, the client loads authenticated `GET /` and shows the home screen with game modes and feature options. The player chooses PvP or Bot from there; keep login independent of game mode and send the selected mode to `POST /api/games`.
- In the PvP lobby, players select a preset and call `POST /api/games`. The server matches them with the oldest waiting player using the same preset or leaves them in a waiting state. A player may have only one active PvP game (waiting or in progress); retries return that queue/game idempotently, and the player can queue again after it ends. Cancel a waiting queue with `DELETE /api/games/:id/matchmaking`. Matchmaking and cancellation use the same global PostgreSQL advisory transaction lock across presets. Do not add public room listing or join-by-room in the MVP.
- When matched, emit `game_started` to both users' authenticated sockets. Players and other authenticated users may subscribe to an in-progress PvP game with Socket.IO `watch_game` and the returned game ID; watching is read-only and never grants permission to submit moves. Validate access, join the Socket.IO game room, then send the latest `game_state` snapshot with preset, remaining clocks, and server timestamp. Commit game changes before emitting Socket.IO events; snapshots must read current persisted state so reconnecting clients recover missed events. Emit each committed move and `game_over` immediately to all subscribers; the per-game queue orders competing actions within one game and does not block other games.
- Store passwords only as bcrypt hashes. Require a valid JWT for protected REST routes and Socket.IO connections; never return password hashes.
- Authentication rules: normalize username/email to lowercase; require usernames of 3–24 ASCII letters, digits, `_`, or `-`; require passwords of at least 8 characters and at most 72 UTF-8 bytes (bcrypt input limit). Use `User.create()` so the `beforeCreate` bcrypt hook runs; do not pass an already-hashed password or use `bulkCreate()` for registration. Use the bcrypt compare helper for login, return the same `401` message for an unknown email and a wrong password, and map database uniqueness conflicts to `409`.
- Sign JWTs with `JWT_SECRET`, include the user UUID as `sub`, and expire tokens after 7 days. Verify the same token for protected REST endpoints and Socket.IO handshakes. Never return hashes or secrets. Rate-limit registration to 5 and login to 10 requests per IP per 15 minutes; the MVP in-memory limiter is single-process only and must be replaced with shared storage before horizontal scaling.
- Keep API contracts documented in `API.md` and preserve the public events/endpoints in the project API documentation.
- Do not add speculative features or dependencies. Daily puzzles need an agreed, valid puzzle collection before implementation.
